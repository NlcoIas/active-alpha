# Think Tank Decisions — Active Alpha Phase 1

> Generated by /plan Think Tank: 3 independent subagent reviews
> Date: 2026-03-28

## Think Tank Members

1. **Technical Architect** — File structure, class diagrams, service interfaces, data flow, design decisions
2. **API/Finance Domain Expert** — State machines, ER diagrams, validation rules, edge cases, API design
3. **UX/API DX Reviewer** — Operational states, simplification, consumer-friendliness, security

## Key Agreements (All 3 Aligned)

1. **Pipeline runs must be persisted in DB** — In-memory status is lost on restart, invisible across workers
2. **Raw SQL for pipeline writes** — ORM overhead is unacceptable for 25k-100k rows/day
3. **Fund-level failures are tolerated** — Pipeline continues with remaining funds
4. **Benchmark failure is critical** — Cannot compute deviations without benchmark data
5. **Admin endpoints need API key protection** — Prevents unauthorized FMP API usage
6. **Consistent error response shapes** — `{error, code, details}` on every endpoint
7. **Pydantic response models on all endpoints** — Self-documenting API via OpenAPI
8. **Ticker normalization is critical** — Both fund and benchmark must use same normalizer for correct joins

## Resolved Conflicts

### Pipeline status: DB table vs Redis-only

- **Architect** proposed Redis with TTL for status (self-cleaning, sub-millisecond reads)
- **Domain** proposed `pipeline_runs` DB table (persistent history, queryable)
- **UX** agreed with Domain (operational necessity)
- **Decision: DB table** — Pipeline run history is essential for debugging. Redis can optionally cache current status for the health endpoint, but the source of truth is PostgreSQL.
- **Rationale:** "Did the pipeline run yesterday? How many tickers failed last week?" requires persistent, queryable data.

### Pagination: Cursor-based vs offset

- **Architect** proposed offset pagination for Phase 1 (simpler)
- **Domain** proposed cursor-based from day 1 (correct for time-series)
- **Decision: Cursor-based** — The deviation table will grow to millions of rows. Offset pagination's O(N) skip cost degrades at scale. Cursor on `(sort_value, id)` is constant time.

### Scheduler: APScheduler vs external cron

- **UX** proposed external cron to avoid duplicate execution with multiple workers
- **Architect** proposed APScheduler with `misfire_grace_time` for missed-run recovery
- **Decision: APScheduler** — `misfire_grace_time=3600` handles server restarts gracefully. Single-worker deployment avoids the duplicate issue. If we scale to multiple workers, add a Redis-based distributed lock.

### Stock prices table: Phase 1 or Phase 2?

- **Architect** noted stock_prices is unused in Phase 1
- **Decision: Include the migration in Phase 1, don't populate it.** The table schema is part of the architecture. Deferring the migration creates confusion when Phase 2 needs it.

## Dissenting Concerns (Noted but Overruled)

1. **Architect concern:** "Redis-only pipeline status is simpler and self-cleaning" — Overruled because operational debugging requires persistent history.
2. **UX concern:** "External cron is more reliable than in-process scheduling" — Overruled because APScheduler's misfire recovery is valuable. Revisit if we deploy multiple workers.
3. **Domain concern:** "deviation_rank should be computed on read, not stored" — Overruled because storing it avoids a window function on every API read. The rank is part of the upsert query anyway (ROW_NUMBER in the same statement).

## Edge Cases Identified by Domain Reviewer

These must be handled in implementation:

1. **Market holidays** — Pipeline must detect and skip (market_calendar.py)
2. **Cash/derivative positions** — Filter via asset_type during normalization
3. **Leveraged ETFs** — Weight sums >100% are valid, don't reject
4. **ETF launches/delistings** — Auto-create new funds, deactivate after 5 empty days
5. **Benchmark rebalance days** — Log reconstitution, use new composition
6. **Stale FMP data** — Compare returned date vs requested date, flag if stale
7. **Duplicate data on re-runs** — ON CONFLICT DO UPDATE makes pipeline idempotent
8. **Ticker symbol changes** — ticker_mappings table + normalize at fetch time
9. **FMP field name inconsistency** — Normalization layer maps aliases to canonical names
10. **Weight sums not ~100%** — Store weight_sum_check, flag quality issues, never normalize
